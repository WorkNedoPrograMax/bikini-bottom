# Spine Pair Review — Bikini Bottom

## Overall verdict

A consumer can source-extract from this pair with high confidence: every `{path.to.token}` reference resolves, every color token carries a hex, the mockup capture is verbatim to a degree rarely seen (positions, timings, radii, the 0.55s stagger all check out against `mockup/bikini-town.html`), and Glossary/UJ/FR names are used verbatim from the PRD. Two gaps have real downstream cost: the Character picker — the one component the PRD explicitly told UX to design (FR-15 note) — has behavioral rules but no visual spec in DESIGN.md, and all four `.working/` mocks are orphans that neither spine links, including the one that *does* design the picker. Fix those two and resolve the wooden-vs-accent button contradiction, and this pair is a clean contract for architecture and story-dev.

## 1. Flow coverage — strong

Checked all four PRD UJs plus new flows against EXPERIENCE.md Key Flows: named protagonist, numbered steps, bolded climax beat, failure path. UJ-1 through UJ-4 are present with titles verbatim from PRD §2.2, all with Maksym as protagonist, numbered steps, and explicit **Climax** beats. UJ-1 has a failure path (no Character picked); UJ-3 and UJ-2 carry their "ignored/unresolved" branches inline; UJ-4 *is* the failure flow. Three new flows (First Run, Send-it-back, Cancel) all follow the same discipline. The quit/relaunch resume path is covered in State Patterns rather than as a flow — acceptable placement.

### Findings

- **medium** FR-13's conversation-lifecycle rule is missing: the PRD says a follow-up continues the same conversation but "handing the same Character a *new* Job from Home Base starts a fresh conversation; the old one's outcome remains on the board as history" (prd.md FR-13). EXPERIENCE.md mentions follow-ups only in passing (IA row "Work Window", State Patterns "A follow-up (FR-13) flips the same Job line back to COOKING") — the fresh-conversation reset and what Maksym sees when it happens appear nowhere. Story-dev will have to go back to the PRD and invent the surface behavior. *Fix:* add a Component Patterns row (or a short Key Flow) for follow-up vs. new-Job: what the Work Window shows when a new Job wipes the chat, and where the old conversation goes.
- **medium** FR-16's landing collision has no experience treatment: the PRD requires "a collision at landing presents as a plain-language choice in the chat" with the Character pausing and going Calling (prd.md FR-16). EXPERIENCE.md covers only the Send-it-back entanglement case (Send-it-back flow step 5, Component Patterns "Send it back"); the collision-at-landing bubble — its copy shape, its Calling trigger, its board status while paused — is unspecified. *Fix:* one row or one flow-step: "Landing collision → Character goes Calling, order WAITING, one either/or bubble; either pick lands consistently."

## 2. Token completeness — strong

Extracted every YAML token in DESIGN.md frontmatter and every `{path.to.token}` reference in the prose of both spines; resolved each against the frontmatter; spot-checked ~40 values against `mockup/bikini-town.html` CSS. All 38 color tokens carry hex values; all component-block references (`{colors.*}`, `{rounded.*}`, `{typography.*}`, `{spacing.*}`, `{components.*}`) resolve; no dangling paths in either file (EXPERIENCE.md uses no token syntax, deferring to DESIGN.md by name — clean). Mockup capture is verbatim: colors, radii, actor positions, animation timings, the 0.55s Voice Line stagger all match. The unassigned `harbor-blue` is documented in prose (DESIGN.md Colors, "kept as a token but unassigned in v1") — good discipline.

### Findings

- **medium** No contrast target is stated for any load-bearing combination — e.g. `{colors.paper-sub}` (#7a5c26) subtitle at 12px on the paper gradient, the four status inks on paper, `{colors.caption-glow}` on `{colors.deep-sea}` (DESIGN.md Colors; EXPERIENCE.md Accessibility Floor covers type size and motion but is silent on contrast). The floor is internally consistent — it never claims a contrast bar — but a consumer restyling any surface has no floor to verify against. *Fix:* one sentence in the Accessibility Floor or DESIGN.md Colors: minimum contrast for board text/status words and chat ink against their papers.
- **low** `spacing.1` (4px) and `spacing.2` (8px) are defined but never referenced by prose or any component token (DESIGN.md frontmatter, spacing block). Unlike `harbor-blue` they carry no "kept deliberately" note. *Fix:* reference them (e.g. label gap 4px, bubble padding) or note them as reserved scale steps.
- **low** A few mockup values that consumers will need aren't tokenized or stated: top-button font-size (14px in mockup `.topbtn`), street speech-bubble text size (`clamp(10px,1.3vw,13px)` in `.wave`), menu subtitle size (12px in `.sub`) — DESIGN.md Components/Typography names these elements but not those sizes. *Fix:* add the three sizes to the typography block or component tokens.

## 3. Component coverage — adequate

Listed every component name used anywhere in either spine, the PRD, and the mocks; checked each for a visual row in DESIGN.md Components and behavioral rules in EXPERIENCE.md Component Patterns (or State Patterns where more natural). Solid on both sides for: Actor, Unseen Dot, speech bubble, wooden top button, Orders Board, Work Window, chat bubbles, input bar, in-chat action buttons, folded technical detail, notification content. Gaps cluster around components EXPERIENCE.md invented that DESIGN.md never dressed.

### Findings

- **high** The Character picker has no visual spec in DESIGN.md. The PRD explicitly assigns this design to UX ("[NOTE FOR UX: the character-picker moment has no visual definition in the mockup — the UX spec must design it]", prd.md FR-15). EXPERIENCE.md gives full behavioral rules (Component Patterns "Character picker": row of portraits, grayed busy states, picked → placeholder swap) and `.working/mock-handout.html` designs it visually (96px chips, `#fffaf0` card, 2px `#3a2c14` border, radius 14px, grayscale busy, picked outline) — but DESIGN.md Components has no row, so the one component with no mockup precedent is exactly the one with no committed visual contract. *Fix:* add a "Crew chip / Character picker" row to DESIGN.md Components, promoting the mock-handout chip treatment to spec.
- **medium** "Cancel this order" has behavioral rules (EXPERIENCE.md Component Patterns "Cancel an order") but no visual definition — DESIGN.md never says what a "quiet affordance near the input bar" looks like (text link? small wood button? which font?), and its placement is itself tagged [ASSUMPTION]. *Fix:* one line in DESIGN.md Components committing its form.
- **low** The volume slider (EXPERIENCE.md "Mute / volume": "long-hover/secondary shows a small volume slider") has no visual spec — the only slider in the product, in a world with no slider vocabulary. *Fix:* a token-level note (wood track? parchment?) or simplify to mute-toggle-only in v1.
- **low** Disabled state for in-chat action buttons is behavioral only ("the buttons then disable", EXPERIENCE.md "Allow / Deny") with no visual treatment in DESIGN.md; the mocks improvise `opacity:.45; grayscale(.6)`. *Fix:* add a disabled appearance to the `action-button` component tokens.
- **low** First Run chrome — step navigation, progress dots, and the green "done" wood-button state that `.working/mock-firstrun.html` introduces (`#6f9a4e`) — is unspecced in DESIGN.md; the flow (EXPERIENCE.md First Run) implies sequential steps but commits no navigation model. *Fix:* either spec the stepper or state that First Run is one continuous Krabs conversation with no stepper (which the flow prose suggests).

## 4. State coverage — adequate

Walked every IA surface (Town, Work Window, Home Base, Orders Board overlay, First Run) against applicable states: empty, cold-load, focus, error, permission-denied, reduced-motion, restart. Strong coverage of the hard ones: empty board copy (Voice and Tone table), quit/crash/sleep and relaunch resume (State Patterns "App quit / relaunch"), reduced-motion with the never-motion-only guarantee (Accessibility Floor), dot persistence across restart, mute persistence, focus ring, M-key suppression while typing.

### Findings

- **medium** Notification permission denied is unhandled: First Run step 4 (EXPERIENCE.md First Run flow) triggers the macOS dialog, but nothing says what happens if Maksym declines — and FR-7's notification click-through is a primary reentry path (prd.md FR-7). The sound/notification matrix assumes notifications always fire. *Fix:* one line: denied → Voice Lines and street signals carry the load; where (if anywhere) Krabs mentions it can be re-enabled.
- **low** Home Base with zero Idle Characters is unspecified: every chip grayed — what does Krabs say, and is the input bar hidden? (EXPERIENCE.md "Character picker" covers busy chips individually, UJ-1 failure covers no-pick only.) *Fix:* one Voice-and-Tone line, e.g. "Whole crew's busy — check the board."
- **low** The Work Window's fresh state for a never-used Character (no Job ever handed) is unspecified — empty parchment, or a greeting bubble? (EXPERIENCE.md IA reaches it via click; no state row covers it.) *Fix:* one State Patterns row.

## 5. Visual reference coverage — broken

Checked that each of the five visual artifacts (`mockup/bikini-town.html` + the four `.working/` mocks) is linked inline at the relevant spine section, with a statement of what it illustrates and a single spines-win-on-conflict rule (the format both bundled examples demonstrate: "→ Composition reference: … Spine wins on conflict."). Only `bikini-town.html` is referenced (DESIGN.md description + Brand & Style; EXPERIENCE.md header note).

### Findings

- **high** All four `.working/` mocks are orphans: `mock-handout.html` (Character picker / UJ-1), `mock-firstrun.html` (First Run flow), `mock-burned.html` (UJ-4 + BURNED board line), `mock-sendback.html` (Send-it-back flow) each illustrate exactly one spine section, and neither spine links any of them. A consumer reading the contract will never find the only visual definition of the picker, the BURNED status in situ, or the serve/send-back bubble pattern. *Fix:* promote them to `mockups/` and add one "→ Composition reference: … Spine wins on conflict." line at each of the four sections.
- **medium** Precedence is stated ambiguously, and never as a rule: DESIGN.md calls the mockup "binding" ("this document captures it; it does not reinterpret it", Brand & Style) while EXPERIENCE.md deliberately overrides mockup behavior in at least one place (board line click-through, Component Patterns "Orders Board toggle", flagged to review M-1). Both are reasonable — capture visuals, override behavior — but no sentence says which document wins when they diverge. *Fix:* one statement, once: "The mockup binds the look; these spines bind the behavior; on conflict the spines win."
- **medium** `mock-sendback.html` diverges from the committed contract in product behavior, unflagged: it adds a "👍 Looks good" approve button and clears the dot on button press, while the spine commits to passive resolution ("result seen … scrolled into view", EXPERIENCE.md State Patterns FR-4 — no approve affordance exists in either spine); the burned/sendback mocks also render *all* choice buttons as plain wood while DESIGN.md specs Allow/Try-again as accent-filled (Components, "In-chat action buttons"). Harmless while the mocks stay in `.working/`, but promoted as-is they contradict FR-4 semantics and the button spec. *Fix:* when promoting, either annotate the divergences or bring the mocks in line.
