Bikini Bottom — UX Design Validation Report

{output_folder}/planning-artifacts/ux-designs/ux-bikini-bottom-2026-07-12/ — DESIGN.md + EXPERIENCE.md

A builder can work from this pair of documents with high confidence: every design token they mention actually exists, every color carries a real value, the capture of the reference mockup is faithful to a degree rarely seen (positions, timings, corner radii, even the 0.55-second voice stagger all check out), and the names for things match the PRD word-for-word. All of these are one-decision fixes, not redesigns, and they are being applied now.

Architecture review — Winston (System Architect)

review-architect-winston.md · 2 critical / 4 high / 5 medium / 6 low

"This spine is better than most: the component table gives behavioral rules, not vibes; the sound matrix is a real matrix; the ASSUMPTION tags are honest." What remains is a different class of problem: the spine makes event-level promises ("dot clears when the result is seen," "work stops within seconds," "silently prepares the folder") whose resolving events are either undefined, defined two contradictory ways, or defined in a way the underlying machinery (Agent SDK, git, macOS) does not offer. Those are exactly the gaps a story developer fills by inventing — and inventions at the resolve-to-clear seam are inventions in the product's core trust guarantee. The two criticals are the same lesson at two scales: name the resolving event.

critical

C-1. Resolve-to-clear has no consistent event model — three contradictory definitions of "seen," and the burned case leaves an undefined Character/board state

EXPERIENCE §State Patterns "Unseen Dot resolve-to-clear"; §UJ-2 step 4; mock-sendback.html
The spine text says passive render-tracking ("scrolled into view"); the sendback mock resolves actively via a "Looks good" button that exists in no spec; the burned case says "a choice made, or the burned explanation scrolled into view" — two resolving events for one need. Follow the scroll branch: need resolved → Character returns to Idle — but the order is still BURNED, the board retires only SERVED and scrapped lines, and one-Job-per-Character makes an Idle Character with a live BURNED order a state the model says can't exist. Underneath sits an unnamed entity: the need itself, which must be a durable per-need record surviving restart. Scroll-into-view is also the expensive choice (intersection observers, per-bubble anchors) for a benefit the mock itself abandons.
Fix: One sentence per need-type naming the exact resolving event (finished = explicit acknowledgment; ask = Allow or Deny clicked; burned = Try again or Scrap it clicked; drop scroll-into-view), plus one sentence on what a resolved-but-not-retired BURNED order means for Character availability.
critical

C-2. The landing-collision ask — the hardest interaction in the product — has no UX definition at all

EXPERIENCE §Key Flows / §Component Patterns (absent); PRD FR-16
PRD FR-16 requires the Character to pause instead of landing silently, go Calling, and ask in plain language which version should win. The spine covers Allow/Deny, Try again/Scrap it, Send it back, even send-back entanglement — and skips the landing collision entirely. No flow, no component row, no copy, no board status while the landing is paused, no statement of what happens to the losing side's work. It is the more frequent case — it happens on the happy path whenever two lanes' honest work touches the same file. This is a hole, not an ambiguity.
Fix: Add the flow (it can reuse the either/or bubble pattern the entanglement row establishes) or explicitly defer it with the same [ASSUMPTION]/Open-Question rigor the rest of the document practices.
